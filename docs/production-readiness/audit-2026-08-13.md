# Production-readiness audit — 2026-08-13

## Decision

**NO-GO. Do not deploy or migrate production.**

The application has strong staging isolation and regression coverage, but the
production release control plane is not yet provisioned. The current public
production endpoint also cannot prove its environment, payment mode, or exact
Git commit. These are release blockers, not items to bypass.

Scope baseline: merged `main` commit
`7731e8b4037720fb2b1dbe1eccd2136115472c52`. This audit made no production
write, deploy, secret change, or migration.

The production identity endpoint previously treated these unknown values as
healthy because strict validation applied only to staging. This audit adds a
production identity guard: a production hostname/project now fails closed
unless every production identity field is explicit and correct.

### GitHub and Cloudflare controls

- GitHub has a `staging` environment, but the API reported no required
  reviewers and no deployment-branch policy.
- No GitHub `production` environment exists.
- `main` has no branch protection rule.
- No production Wrangler configuration or production deployment workflow is
  committed. The only Wrangler deployment path is the staging-only workflow.
- Repository-scoped legacy E2E credentials still exist. The nightly release
  readiness workflow used those generic names without an environment guard.
  It is changed in this audit to use only the GitHub `staging` environment,
  one staging-only password, fixed synthetic identities, and the fixed staging
  Worker.
- Three older RLS workflows referenced generic live-target variables in
  pull-request-triggered jobs. Those generic credentials were absent and the
  live checks skipped, but provisioning them later would have exposed a target
  to same-repository PR code. Their live jobs now run only after a push to
  `main`, use the protected `staging` environment, and consume only `STAGING_*`
  secrets. Pull requests rely on credential-free migration replay and
  static/unit controls.
- Cloudflare production Worker settings, token scope, routes, custom-domain
  ownership, WAF/access rules, and version rollback availability have not yet
  been exported and reviewed. Do not infer them from the public hostname.

### Supabase migrations

- Production migration history has not been read and compared to the canonical

  separate, environment-specific operation after Vault values are provisioned.
- Disposable migration replay passes on merged main, but replay success does
  not replace a production baseline query, backup/restore drill, or maintenance
  plan.

### Stripe separation

- Code selects sandbox only for `APP_ENV=staging` and live only for
  `APP_ENV=production`, and rejects mismatched direct key types.
- Tracked browser configuration contains a sandbox publishable token in
  development and a live publishable token in production. No server secret-like
  variable was found in the tracked environment files.
- Runtime production Stripe mode is currently unknown. Live catalog IDs,
  prices, webhook destination/signature secret, tax behavior, customer portal,
  and one low-risk live transaction/refund have not been verified.

### Existing product/legal blockers

`docs/release-readiness/blockers.md` remains authoritative. In particular,
real student/IEP release remains blocked by malware scanning, backup restore
and incident-response proof, and legal/privacy review. Email authentication is
also required before production notification email is enabled.

## Blocking actions

1. Protect `main`: require pull requests, required CI checks, resolved
   conversations, no force push/deletion, and an intentional admin policy.
2. Add reviewers and a protected-branch deployment policy to `staging`.
3. Create a GitHub `production` environment with required reviewers and a
   `main`-only deployment policy. Store only production-specific secrets there.
4. Remove legacy repository-scoped E2E credentials after every remaining
   workflow is migrated to synthetic staging identities or credential-free CI.
5. Export and review Cloudflare production configuration. Create a
   production-only Wrangler config and manual, approval-gated workflow in a
   separate PR only after identities are verified.
6. Configure production `APP_ENV`, `VITE_APP_ENV`, live Stripe client token,
   exact Git SHA, canonical origin, cron origin/secret, Supabase URL and
   publishable/service credentials. Never copy staging values.
7. Read production `supabase_migrations.schema_migrations`, compare it to all
   178 canonical filenames, and review the exact forward-only delta.
8. Complete a recoverable backup plus restore drill before applying the delta.
9. Verify live Stripe catalog/webhook separation and run the approved payment
   smoke/refund procedure.
10. Close all P0 real-record blockers in
    `docs/release-readiness/blockers.md`.
11. Run the release checklist against the exact approved commit and attach
    artifacts. Change `audit-state.json` to `go` only in the evidence PR.

## Controls added by this audit

- Strict production identity evaluation at `/api/public/env-health`.
- Credential-free production-readiness contract CI.
- Nightly release readiness pinned to protected staging credentials, all seven
  roles, staging identity checks, and exact Git SHA parity.
- Default ignore rule for any new `.env*` file; only the three reviewed public
  configuration files remain allowlisted and contract-tested.

None of these controls performs a production operation.
