# Legacy Document Privacy and Hard-Delete Boundary

Sixth separate review draft, after the five permission drafts. No canonical migration or ledger entry; no hosted execution is authorized.

The current reader ignores legacy visibility labels, while the old platform-admin policy allows raw document deletion without student access. This draft tests those baseline failures and prepares a combined containment boundary.

Only `team` means implicit student-team sharing. Existing `private`, `family`, `student`, unknown and null labels are preserved; they do not become team visibility automatically. A current eligible uploader or a fresh, currently valid individual full-document grant can still satisfy visibility. All preceding student-access, partner-only, original-file, archive and quarantine checks still apply. An uploader who loses student access has no permanent exception. Original rows, Storage reads, raw extraction/summary rows and the reviewed-summary projection share this boundary. A summary-only relationship remains able to read team summaries without obtaining original access.

The labels alone do not prove a parent/family relationship, legal authorization or a particular intended audience. This is conservative containment, not a new interpretation of legal/family access. A later explicit review/change workflow must resolve retained restricted records; the draft does not silently normalize them. Existing explicit grants do not evade the preceding lifecycle retirement rules.

New ordinary-account uploads accept only the supported `team` scope, both in the application intent parser and restrictive database INSERT policy. Visibility, uploader and student identity become immutable on existing document rows, including trusted updates; future reassignment/reclassification requires a separately reviewed change. Ordinary metadata edits remain available when both current editing and original-view access permit them. Old unsupported upload/recovery attempts must be reconciled during the separately reviewed cutover preflight, not replayed or discarded automatically.

Ordinary accounts cannot hard-delete document rows or registered original files, even if a future permissive policy or restored DELETE grant is added. Trusted service/database cleanup stays separate. The file cleanup predicate permits only current non-partner editing accounts to remove unregistered student uploads, preserving other buckets' existing policies. Its actor comes from `auth.uid()`; anonymous and unrelated probes return false. The BEFORE DELETE guard rechecks fresh state after the object row lock, preventing a stale RLS snapshot from deleting bytes registered by a competing transaction. No existing row, label, object or grant is rewritten/deleted by installation.

The complete disposable job retains the 56 inherited installer/catalog stages, then all five prior permission installers before this draft. It verifies both patched reader routines' metadata, every unrelated public routine, existing policies/triggers/indexes, row data and all table privileges except the explicitly revoked ordinary document DELETE. Two fixed-path definer predicates and two private invoker triggers are separately inventoried. Only the narrow cleanup predicate is executable by anonymous/authenticated callers; it returns no document identity or content.

This is not a hostile database-owner boundary, parent-student cascade-delete review, whole-platform privacy approval, provider/worker acceptance or retroactive revocation of signed URLs/copied data. Other data scopes, broader rights-status consistency, canonical packaging and final combined/hosted testing remain open. Fresh scoped authorization is required before any migration, deployment or publication.
